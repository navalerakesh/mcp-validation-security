# Schema Compatibility And Migration

MCP Validator public JSON artifacts identify both `documentType` and `documentSchemaVersion`. Consumers must validate both values before reading an artifact.

Schema versions use semantic versioning:

- Patch releases clarify schemas without changing accepted document shapes.
- Minor releases may add optional properties or enum members. Consumers must ignore unknown properties and handle unknown non-gating enum values explicitly.
- Major releases may remove, rename, or change required properties and require a consumer migration.

The validator supports well-formed artifact versions with the current major version. Assurance-result schema `3.x` additionally has an explicit legacy `2.x` read path; this exception does not apply to other artifact types. Unknown document types, malformed versions, V1 score/trust results and unsupported future major versions are rejected by `ArtifactContracts.IsCompatible`.

Published schemas are under `docs/Schemas`. A major schema release must add migration notes and retain a rejection fixture for incompatible artifacts. V1 score/trust/verdict artifacts cannot be converted losslessly into V2 claims and certificate evidence, so the runtime does not provide a compatibility converter.

Audit manifests hash the final bytes of every subject artifact listed in `artifactPaths`. The manifest does not list or hash itself, avoiding a recursive self-digest contract. Signed validation attestations independently bind the canonical result bytes to an ECDSA P-256 public key.

Assurance-result schema `2.0.0` uses document type `mcpval.assurance-result`. It requires typed claims, independent assessments, evidence summary, certificate eligibility, and a V2 policy decision. It removes serialized global score, L1-L5 trust, baseline verdict, and generic overall status fields. Baselines must use the same assurance profile and profile revision.

Assurance-result `2.1.0` adds optional catalog-enumeration evidence and tool-schema inspection outcomes. Existing `2.0.0` artifacts remain readable; missing new fields are unavailable evidence, not completed inspection. Raw observed entries, recovered entries, rejected entries, page attempts, parsed/rejected pages, payload characters and termination remain distinct. Raw observed counts are not total-catalog estimates when enumeration is incomplete. Dictionaries of opaque cursor values are not persisted.

Assurance-result `2.2.0` adds optional `measurements.protocolCompliance.optionalCapabilityObservations`. Entries identify the capability, method, declaration, probe invocation, nullable support, response classification and optional HTTP status. Optional `preparationMethod` attributes catalog-preparation failures without claiming the completion method was dispatched. `attempted` means the method probe was invoked, not that a receiver observed it: local admission may block dispatch. Missing observations or nullable support are not pass credit. The schema rejects unknown classifications, success without invocation/support, success with a non-2xx HTTP status, and support claims inconsistent with method-error evidence. Existing `2.0.0` and `2.1.0` artifacts remain readable.

Outcome taxonomy `1.1.0` appends `policyBlocked` to the probe classification vocabulary without renumbering existing values and maps it to canonical `blocked`. Explicit operation, target and budget denial is distinct from authentication-required or unavailable transport evidence. Consumers must not infer target noncompliance from local denial. This does not claim that every legacy measurement already carries the complete obligation ledger; that recovery work remains tracked separately.

Assurance-result `2.3.0` persists individual extension `coverage` declarations, including planned-but-unstarted obligations, separately from core coverage. Resolved scenario inventory is captured before category execution; interrupted execution and failed planning retain unavailable/cancelled obligations without pass credit. Earlier artifacts without individual extension coverage remain readable but do not establish that the newer obligation inventory was captured. Coverage vocabularies accept the defined string and numeric enum encodings, not arbitrary values.

Post-run policy and provider interpretation use recorded completion time, falling back to recorded start time for unfinished results. Pre-execution authorization admission still uses the live clock. Saved-result loading requires a well-formed, explicitly zoned `startTime` and, when present, `endTime`; absent, timezone-free or ambiguous timestamp aliases fail local usage validation instead of receiving the replay machine's current time. Do not repair old artifacts by inventing timestamps: recover the original trusted timestamp or preserve the input as unavailable evidence. Historical interpretation is not a new authorization grant.

Explicit validation output now publishes one per-run directory under `--output`. Markdown, HTML, canonical JSON, SARIF, JUnit, optional companions/attestation and the audit manifest are staged together, then become visible at one directory-rename boundary. Audit subjects remain sibling filenames and bind the final bytes. Use returned artifact paths or recurse into the per-run directory instead of assuming flat files directly under the output root. `.pending-*` directories are not committed bundles; graceful failures remove owned staging, but process crash/power loss and hostile filesystem races are not claimed covered. Already-finalized cancellation/error evidence gets a separate 30-second publication budget without resuming target execution.

The MCP wrapper reads a single committed bundle or a legacy flat result, ignores staging directories, rejects ambiguous/missing successful captures, and bounds artifact bytes using its existing CLI-output limit. These failures are local runtime-integrity errors, not target noncompliance.

Assurance-result `3.0.0` is a breaking numeric-shape change within the typed assurance document model: unmeasured operational percentiles/rates and target CPU/memory/network fields are nullable instead of fabricated zeroes. Bounded percentile windows carry observed/retained/discarded/rejected counts and `mostRecent` strategy. Actual local resource observations are explicitly validator-process scoped, including concurrent activity, not target-server telemetry. Consumers must handle null as unavailable, not zero or pass.

Loading a `2.x` assurance artifact normalizes zero-denominator operational values to null, preserves genuine measured zero, records the original version in `run.sourceDocumentSchemaVersion`, and uses the current in-memory document version. Legacy target-resource values and limit flags lack resource-measurement provenance and become unavailable in the migrated view; transport request counters remain. Baseline comparisons preserve the source version. Original input bytes are not rewritten; an old signature still binds those original bytes, not a reserialized migrated document. Missing sample-window or resource provenance is not invented.

Catalog enumeration is bounded to 50 pages, 4,096 processed entries, 16 Mi retained payload characters and 4,096 cursor characters per catalog. Resource processing also respects its configured lower item limit. Authentication-required, cancellation, malformed page, transport failure, repeated cursor and budget termination remain separate from normal traversal completion. Rejected entries prevent a complete-catalog claim even when the last page was reached.

Schema guidance inspection uses JSON Schema draft 2020-12 (published 2022-06-16), including local JSON Pointer references, reference siblings, type alternatives, and separate `allOf`/`anyOf`/`oneOf` branches. It does not replace full schema validation or flatten a schema into a purported equivalent schema. Work is bounded to 4,096 indexing/inspection steps, depth 64 and 32 alternatives. Unknown dialects, external/dynamic references, nested resource scopes and unsupported conditional/pattern-dependent interpretation remain explicitly incomplete. Partial findings can be retained, but an incompletely inspected catalog has no aggregate readiness score.

Synthetic candidate generation is narrower than normative schema validation. It uses at most 64 generated values, depth 16, 64 Ki schema/candidate characters and 4,096 characters per copied literal. It declines unresolved, alternative-dependent or regex-dependent generation and requires the candidate to pass the existing validator against the original schema before dispatch. Missing schema, unsupported generation, exhaustion or a rejected candidate is inconclusive, not proof of target noncompliance. A schema-valid synthetic argument set is not proof of harmless application effects; execution policy still governs admission.

Client-profile summaries, model-evaluation companions, and audit manifests also use `2.x` contracts. V1 companions are incompatible by design.

Audit manifest `2.1.0` adds optional `configurationSources`. Each entry identifies a canonical setting path, source (`default`, `file`, `profile`, `commandLine`, or `governance`), non-secret pointer, replaced source and override reason. It contains no setting values, raw file paths or arbitrary dictionary-key text. Existing `2.0.0` manifests remain readable and are not assumed to contain this evidence. Execution plans carry the same projection; offline-report session receipts include only their reporting settings. This operational metadata does not change canonical findings or scoring.

Configuration input has a separate `schemaVersion` contract, currently `1.0.0`. Omitting it preserves legacy interpretation; adding it does not alter normalized settings. Unsupported explicit versions fail preflight rather than being interpreted as current. The [published schema](Schemas/mcpval-configuration-v1.schema.json) is generated from CLI serializer metadata with `mcpval config-schema`; the [configuration guidance](../Mcp.Benchmark.CLI/README.md#configuration-files) describes migration and parser-only limits. This input version is independent of artifact and MCP protocol versions.

The `mcpval.official-conformance-evidence` wrapper has its own `1.x` contract. Import verifies the document contract, bounded structure, exact scenario check digests, pinned runner/package/requirement-set provenance, and target/protocol binding. Audit manifests bind the imported wrapper SHA-256 under `externalEvidenceSha256`.
